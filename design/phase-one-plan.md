# 第一部分开发进度计划：租户、系统、管理员与审计

更新日期：2026-09-14。状态：计划草案，供 Owner 审阅；业务表设计和功能开发尚未开始。

## 1. 本期目标与现状

目标是在独立权限中心内完成“管理员进入后台 → 管理租户 → 分配租户管理员 → 创建租户内系统 → 生成并验证系统密钥 → 查询操作审计”的完整管理流程。

目标后端仓库：`E:\goland\projects\olixops-permission-center`。本计划以后端交付为主，独立管理前端作为随后衔接阶段，仓库位置待确定。

现有 Go 项目已经具有 DDD 骨架、Gin、gRPC、PostgreSQL/GORM、Redis、zap、外部 JWT 验签、分页/统一响应、健康接口和可选 SpiceDB 客户端。本次已核对源码：HTTP 业务入口目前只有健康检查与当前身份；gRPC 只注册健康服务。租户、管理员、系统、系统密钥和业务审计仍待实现。

[AGENTS.md](../AGENTS.md)、[README.md](../README.md) 和 [database.md](database.md) 中仍有“全局系统、租户开通系统”的旧描述。后续以用户已确认的以下边界为准，并在阶段 P1 同步修正文档。

## 2. 已确定的业务边界

- 系统必须且只能属于一个租户；一个租户可以拥有多个系统，租户之间的系统和业务内容独立。
- 权限中心用户与租户多对多；同一用户可管理多个租户。
- 后台角色只有平台超管、租户管理员。登录身份通过认证后仍需检查本地用户状态和管理员关联，不自动取得管理权。
- 系统账号独立于后台用户；一期每系统一个账号，账号可以有多把密钥以支持轮换。
- 认证密钥绑定账号，账号绑定系统，系统绑定租户；作用域从认证结果推导。
- 日志分为 zap 运行/访问日志和可查询的业务审计记录；业务审计不记录认证密钥、JWT、Cookie 或完整敏感请求。
- 本期实现租户、管理员、系统和密钥的管理审计。系统给业务资源授权的审计随第二部分的授权接口实现。
- SpiceDB Schema、业务用户/资源关系、授权/撤权、权限检查、授权同步任务属于第二部分。本期不创建 `authorization_outbox` 或业务授权镜像表。

## 3. 拟设计的 7 张核心表

这里是职责清单，尚不是批准的表结构。完整字段、索引和 SQL 在 P1 写入 [database.md](database.md)。

| 表 | 职责 |
|---|---|
| `tenant_info` | 租户编码、名称及状态 |
| `system_info` | 系统信息及唯一租户归属 |
| `user_info` | 后台用户、外部身份映射、状态及固定平台角色 |
| `tenant_member_info` | 后台用户与租户管理员的关联 |
| `system_account_info` | 系统调用账号及状态 |
| `system_credential_info` | 密钥标识、不可逆校验值、有效期、吊销状态及账号归属 |
| `authorization_audit_log` | 管理操作的追加审计记录，第二部分复用其记录规范 |

表设计覆盖审计字段、软删除、唯一性与索引范围、并发重复请求、状态变化以及历史查询。业务表不使用外键；审计历史只追加，不提供更新和删除接口。具体字段必须满足根目录开发规范。

## 5. 各阶段需要落实的规则

### P1：先形成可审阅设计

- 更新旧模型描述，写明三类身份：后台管理员、系统调用账号、第二部分的业务用户。
- 默认沿用现有外部 RS256 JWT；确定可信身份到 `user_info` 的映射，以及首个超管的受控初始化步骤。
- 当前代码没有用户名密码登录或 JWT 签发。如果需要自建登录，在本阶段补充登录、密码和令牌生命周期方案后再调整计划。
- 明确首次建库、版本迁移、唯一索引、软删除后的编码复用规则，以及事务边界。
- 明确最后一个有效超管的保护规则、租户无管理员的恢复方式、停用与恢复、软删除条件。本期不设计跨租户迁移系统。
- 形成 HTTP 管理接口清单与 DTO；明确系统密钥认证在 HTTP 和 gRPC 中的传递方式。管理 CRUD 优先 HTTP，系统身份探测复用同一应用用例。
- 固定返回结构与错误语义；分页统一 `pageNum/pageSize` 入参和 `total/list` 响应。

[AGENTS.md 第 6 节](../AGENTS.md) 要求：“Owner 确认后才能编写相关 model、repository、migration、handler 或自动建表代码”。本次对整体方向和进度计划的认可，不替代对尚未编写的具体表结构的审核。

### P2/P3：后台权限与租户管理

以下是拟定的首期操作范围，随 P1 权限矩阵一起审阅：

| 操作 | 平台超管 | 租户管理员 |
|---|---|---|
| 创建、编辑、停用租户 | 可操作所有租户 | 查看自己管理的租户 |
| 后台用户管理、分配或移除租户管理员 | 可操作 | 不自行提升或分配管理身份 |
| 管理租户内系统、账号和密钥 | 可操作所有租户 | 仅所属租户 |
| 查询管理审计 | 全局 | 仅所属租户 |

后台 JWT 身份与系统密钥使用明确的认证入口，不通过“JWT 校验失败就尝试系统密钥”混用认证。敏感操作每次检查本地有效状态；列表、详情和变更使用同一范围规则。

租户和用户停用后即使 JWT 尚未过期也不得继续操作；删除/停用保护规则在事务中处理，覆盖并发移除管理员等场景。发生关系移除或停用后，不能依赖长时间缓存过期才生效。

### P4：系统与密钥

- 创建系统时固定租户归属，系统编码唯一性按 P1 确定的范围实现。
- 系统账号、密钥的停用和恢复行为分别定义；恢复系统不自动复活已吊销密钥。
- 密钥随机生成、创建响应中仅展示一次；数据库只保留不可逆校验值及必要元数据。签发超时后不能通过“查看详情”取回原密钥，应定义重新签发的处理方式。
- 轮换允许新旧密钥在受控时间内并存；过期、吊销或上层停用后拒绝调用。
- 提供受认证的系统身份探测能力，验证实际所属租户、系统和账号。公开健康接口仍只证明服务存活，不作为密钥有效性的证明。
- HTTP/gRPC 共用账号校验与范围解析；这一步不调用 SpiceDB 的业务授权接口。

### P2/P5：审计

- 记录可信调用者类型与 ID、目标租户/系统、对象、动作、必要的脱敏变化、结果、时间和请求 ID。
- 管理数据的成功变更与成功审计在同一 PostgreSQL 事务提交；失败/拒绝事件另行安全记录，并定义审计存储故障的处理。
- 保留必要名称快照，避免用户或系统软删除后无法理解历史。密钥创建/吊销事件只记录密钥标识，不记录明文或完整认证头。
- 支持按租户、系统、操作人、动作、时间范围、结果和请求 ID 查询，索引配合实际筛选条件。
- 审计记录不提供修改/删除接口；普通访问日志与业务审计分开管理。

## 6. 第一部分后端验收用例

1. 受控初始化首个超管，完成外部身份与后台用户映射；无管理身份的有效 JWT 仍被拒绝。
2. 创建租户 A、B；同一用户可以同时管理两者，另一个用户仅管理 A。
3. A 的管理员无法读取或变更 B 的租户、系统、账号、密钥和审计；列表与 `total` 同样隔离。
4. A、B 分别创建系统，生成各自密钥；不能通过修改请求参数跨系统或跨租户操作。
5. 密钥只在创建响应展示；详情、列表、日志、审计中均无明文。验证轮换、过期、吊销与并发请求。
6. 移除管理员、停用用户、租户、系统或账号后，相应访问被拒绝；恢复行为与设计一致。
7. 每次管理变更都有可追踪审计，失败路径可定位；分页、参数错误、401/403、统一响应及 trace-id 符合契约。
8. 使用 PostgreSQL 验证迁移、事务回滚、唯一性、软删除和并发保护；仅 mock 测试不替代这些验证。
9. 执行修改范围的 gofmt、`go vet ./...`、`go test ./...`、相关构建和接口文档检查，记录实际结果与未执行原因。
10. 在 SpiceDB 禁用时仍可完整验证本期管理功能，避免把第二部分作为本期交付的隐含前置条件。
